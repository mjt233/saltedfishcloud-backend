## 一、安全与信任边界

### 1. 网关 JWT 密钥与 core 人工同步

网关的验签密钥来自环境变量 `SFC_JWT_SECRET`，而 core 的密钥存在数据库配置项 `sys.safe.token`（首次启动随机生成）——**两侧一致性完全靠部署保证**，没有自动对齐机制。
漂移的症状很隐蔽：**登录正常，但经网关访问 `/api/ext/**` 全量 403/7005**，容易被误判成"网关坏了"。
到期条件：安全阶段（阶段 5）引入密钥分发机制，或 core 侧提供"导出/对齐"入口。见[网关设计 · 决策 3.5](microservice/microservice-gateway-design.md)。

### 2. 网关不感知密钥在线变更（无热更新、无轮换）

core 支持在线修改 `sys.safe.token`（改后所有已签发凭证立即失效），但网关只读**启动时**的环境变量，不做热更新。
因此改密钥必须**同时**改网关环境变量并重启网关，否则出现第 1 条的漂移症状；轮换期间还存在"新旧密钥并存"的空窗期。
到期条件：安全阶段一并设计（阶段 5 待答问题 6 已把"签名材料的分发与轮换"列为必答项）。

### 3. 网关不校验 Redis 会话白名单（登出 / 改密不即时失效）

core 的完整校验＝「验签 ＋ 过期 ＋ Redis 白名单（`sfc:token:{uid}::{token}`）」，网关只做**验签 ＋ 过期**。
后果：用户登出 / 改密 / 被踢下线后，旧凭证在**网关这一层仍然算已认证**；只有拿凭证原值去找 core 的下游才会被拒。
到期条件：安全阶段；或在网关引入 Redis 依赖（本轮明确不做，因为那会把 key 规则复制出第二份）。

### 4. 凭证原值透传到微服务（日志与采样暴露面）

为了让下游能自行完成含白名单的完整校验，网关把 `Token` 头 / `token` Cookie / `?Token=` **原值透传**给微服务。
代价是 30 天长效凭证会进入微服务的访问日志、异常堆栈与监控采样——**微服务不得打印凭证**目前只是部署侧的口头约束，没有技术强制。
到期条件：安全阶段换成短时、受众绑定的载体；在此之前，部署文档与代码评审都要反复强调这一条。

### 5. 信任模式本身：微服务只信明文头 `X-Sfc-Uid`

微服务读网关注入的 `X-Sfc-Uid` 作为"当前用户"，**不做任何校验**；任何能直连微服务端口的人都能伪造任意用户。
当前唯一兜底是"微服务与 core 的内部接口只允许内网 / 本机可达"，而这是**部署约束而不是技术约束**。
到期条件：**上公网前必须先完成阶段 5**（可验证载体 ＋ fail-closed）。

## 二、已验证的边界（记录在案，不是待办）

### 6. 请求体方向的内存占用与体量同阶

实测：网关 `-Xmx512m` 下，65 / 128 / 256MB 请求体（`Content-Length` 与 chunked）均完整通过，**≥512MB 必失败**（`OutOfDirectMemoryError` → 500/0），客户端限速 50MB/s 亦然。
本轮不处理（先完成轻量化流程）；已知缓解是放宽 `-XX:MaxDirectMemorySize`，根治要在请求方向实现端到端背压或走数据面旁路（阶段 9）。
见[网关设计 风险 12](microservice/microservice-gateway-design.md)。

### 7. core 透传分支（`/api/**`）的大上传未实测

上述边界是在**代理分支**（`/api/ext/**`）测出来的；它是否同样作用于 core 透传分支的大文件上传**尚未验证**（当时探针实例被中止）。
在补齐之前**不得宣称"core 的 8GB 上传经网关可用"**。
到期条件：用真实上传用例（≥512MB）在 `/api/**` 上复测并记录数字。

### 8. 传输层与业务契约不一致的两处

① 非法百分号转义（`%2` / `%zz` / `%`）在 **Netty 解析请求行**时即被拒，返回**空体 400**，拿不到业务码 7000；② 超长路径（>4096）在网关逻辑之前被 Netty 以 **414** 拒绝。
两者都属 HTTP 传输层硬限制，任何应用层实现都无法绕过；**不要**为此再写一份"更早的路径规则副本"。
见[网关设计 风险 11 / 17](microservice/microservice-gateway-design.md)。

### 9. 网关是可用性单点

网关挂掉 = 整站不可用（入口唯一）；当前没有多副本前置 LB、没有 HA 方案。
入口切换时保留了"浏览器直连 `core:8087`"的回退路径，但这只是**回退**而不是高可用。
到期条件：部署阶段（多副本 + 前置 LB / Ingress）。

## 三、未完成的功能

### 10. 浏览器点击级回归未完成

8.6 只做到 **HTTP 级等价**（13 个用例经网关与直连状态码 / 字节数 / SHA-256 全一致，登录、`Set-Cookie`、`/api/ws` 握手、OIDC discovery 均通过）。
登录、上传 / 下载、播放、WebSocket 通知、插件页面与（若启用）OIDC 授权码流程的**点击级回归仍待人工确认**。
清单见[预研报告 §六](microservice/microservice-gateway-spike-report.md)。

### 11. 档位 2（阶段 6）没有设计文档

"远程核心能力"是全项目难度最高、学习价值最高的一块（跨进程流式语义），当前只有路线图 6.4 的一行占位。
身份传递会继续沿用框架期契约（core 按 `X-Sfc-Uid` 装载主体，无该头一律 401），但**流式通道怎么设计还没动笔**。
到期条件：阶段 6 启动前先补设计文档（[评估报告 🟠-4](microservice/review/microservice-plan-review.md)）。

### 12. 阶段 7 的清单与静态资源代理未实现

`GET /api/ext/manifest`（扩展清单）与 `/api/ext/{svc}/static/**`（静态资源代理）都只有**路由位**，没有实现。
⚠️ 静态资源是**匿名**链路：**必须连同路径校验一起放行**，在实现之前**不得**把该前缀加入任何放行规则（先放行后补校验 = 留出未被消费的攻击面）。
见[网关设计 · 决策 7](microservice/microservice-gateway-design.md) 与[档位 3 §7.6](microservice/microservice-phase3-frontend-integration.md)。

### 13. 阶段 9 数据面预签名直连暂缓

信任模式下 URL 里的"凭证"没有安全语义，预签名直连会退化成"带 uid 的明文链接"，因此整体暂缓——框架期下载走网关流式代理。
暂缓项清单（载体与 TTL、资源绑定、Nginx 直连路由、URL 模板用同一个配置项切换）已记在[路线图阶段 9](microservice/microservice-roadmap.md)。
到期条件：随安全阶段一起重做。

### 14. `microservices/` 两个工程已进入 root `<modules>`（构建耦合回归）

早先的约定是工程"不进 root `<modules>`"（避免改微服务就要重建宿主）；现状是 `sfc-demo-service` 与 `sfc-gateway` **都在** root `<modules>` 中，根目录 `mvn package` 会一并构建。
好处是一次构建拿到全部产物，代价是耦合回归。**不继承 root pom** 与**零咸鱼云依赖**这两条硬标准仍然成立，可用 `mvn dependency:list` 逐条核验。
到期条件：如果在意"独立构建"的纯粹性，从 root `<modules>` 移除这两项即可（各工程的 `-f` 构建命令不受影响）。
