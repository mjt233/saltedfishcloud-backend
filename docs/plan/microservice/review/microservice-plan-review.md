## 0. 总体结论

**四份文档整体合理、可以按路线图推进。** 质量明显高于常见设计文档水准：排序原则自洽、决策记录带证据与备选、能力边界如实记录、验证标准可测。未发现方向性错误。

| 文档 | 结论 | 一句话评价 |
|---|---|---|
| 路线图 | ✅ 可直接用作执行主线 | "每步只引入一个新变量"原则贯彻到位，节奏设计（两个休息检查点）符合学习曲线 |
| 档位 1 设计 | ✅ 定稿质量高，可实施 | 决策记录规范，SPI 契约取舍有论证；2 处隐式约定需补成文 |
| 依赖冲突调试手册 | ✅ 四份中"可直接照做"程度最高 | 把试错式调试转化为系统化方法论，是本套文档的最大亮点之一 |
| 档位 3 设计 | ⚠️ 方向正确，作为"定稿"尚有 4 处设计细节需补齐 | 安全主线（UID/PATH）识别准确，但令牌绑定、代理安全细节、预签名 URL 形态未定 |

**专项结论（是否需要独立 Gateway 组件）**：**当下不需要，方案"sfc-core 自带代理 + 数据面可选 Nginx"是正确选择**（详见 §2，含未来引入的触发条件）。

**主要保留意见**（不影响档位 1 启动，影响档位 3 实施与档位 2 启动）：

1. 内部服务令牌未定义 `scope` 语义、未绑定目标服务（防跨服务重放）
2. 自建代理未提及 hop-by-hop 头处理 / `X-Forwarded-*` 重写等经典网关安全细节
3. 预签名 URL 的形态随部署模式变化（直连 `/dl/{token}` vs Nginx `/dl/{service}/**`），未统一
4. **档位 2（阶段 5~6）没有设计文档**，而它恰恰是全项目难度最高、学习价值最高的部分

详见 §6 问题清单（分级）。

## 2. 专项评审：是否需要独立 Gateway 组件

### 2.1 方案现有的网关立场（梳理）

四份文档没有出现"独立网关组件"，其网关角色由三部分隐性承担：

| 承担者 | 覆盖职责 | 文档位置 |
|---|---|---|
| **`sfc-core` 内的 `ServiceProxyController`** | 控制面反向代理、流式管道、轮询负载均衡、故障重试、503/404 语义、内部令牌签发、UID/PATH 信任边界 | 档位 3 §7、路线图阶段 8 |
| **微服务自身** | 静态资源 `GET /static/**`、数据面下载端点 | 档位 3 §4.3、§8 |
| **Nginx（可选，阶段 9.3）** | 数据面 `/dl/{service}/**` 直连路由，绕过 core 进程 | 档位 3 §8、路线图阶段 9 |

治理能力（熔断、限流、链路追踪）被**明确排除**在档位 1、3 之外（档位 1 §1"明确不做"、档位 3 §1"明确不做"），两处口径一致。

### 2.2 论证

#### 观点 A：引入独立网关（Spring Cloud Gateway / APISIX 等）的理由

1. 业界微服务标配，SCG/APISIX 的使用经验本身有市场价值
2. 代理的线程、带宽开销从 core 进程剥离
3. 限流、熔断、灰度等治理能力开箱即用

#### 观点 B：方案"sfc-core 自带代理"的理由（按用户视角逐条检验）

1. **学习收益最大化（成立，且是决定性理由）**。路线图检查点 3 的学习点是"网关模式、信任边界与鉴权传递、控制面/数据面分离"——这些能力**只有亲手实现代理才能获得**：流式管道、实例选择与重试、503 语义、令牌信任边界。装一个 SCG 会把这些学习点退化成"背配置项"。按用户确认的评估视角（收益仅计学习价值），方案的选择明显更优。
2. **部署形态匹配（成立）**。学习项目、单人开发、NAS/局域网部署，无多消费者高并发场景，独立网关的运维成本（又一个组件、又一套配置、又一轮依赖冲突）无对应收益。
3. **与既有安全设施共生（成立，且是本方案特有的结构性理由）**。`@UID`/`@ValidPath`/`ProtectBlocker` 都在 core 的 Controller/拦截器层生效（档位 3 §7.4 的安全红线正是基于此）。代理放在 core 内部，信任边界天然连续；换成独立网关，这些校验要么重建一份、要么改为网关侧令牌校验——改造量与风险都反而上升。方案的 §7.4 分析实际上已经论证了这一点，只是没有把它上升为"为什么不引入独立网关"的显式结论。
4. **避免再开一条依赖冲突战线（成立）**。SCG 是 reactive/Netty 栈，与本项目刚在阶段 3 打完的插件类加载器战争属于同一量级的麻烦，学习收益却远低于阶段 3（那是"类加载与依赖隔离"，这是"如何配置一个中间件"）。

#### 平衡项：SCG 知识的缺口

按纯学习视角，唯一损失的是"业界标准网关怎么用"这个知识面。这可以用**可选延伸实验**补齐（见 2.3 建议），不需要进入主线。

### 2.3 结论与建议

**结论：不需要独立 Gateway 组件。** "core 自带控制面代理 + 数据面可选 Nginx"正是控制面/数据面分离的标准架构——数据面的 Nginx（阶段 9.3）本身已经是"独立网关"思想在数据面的体现。方案隐式地做出了正确选择。

**建议补两件事**：

1. **把这个结论显式写进方案**（一句话即可，如加在档位 3 §1"明确不做"表中）。目前它是隐式立场，审阅者需要自己拼出来。
2. **写明未来引入独立网关的触发条件**，避免"没做"被误读为"没想到"。建议表述：
   - core 需要横向扩展多副本（需要前置 LB）；
   - 出现真实的限流/熔断需求；
   - 出现多团队多消费者；
   - 需要统一 TLS 终结。
   满足其一再评估，且届时优先评估 Nginx/APISIX 而非 Spring Cloud Gateway（避免 reactive 栈引入）。
3. **可选延伸实验**（不进主线）：档位 3 完成后，用 Nginx 复刻 `/api/ext/**` 的代理规则，与手写代理对比——低成本补齐"标准网关"知识面。

### 2.4 附加发现：自建代理必须补的安全细节

选择自建代理 = 选择自己承担网关的安全细节。档位 3 §7.5 的"必须流式、禁止 byte[] 缓冲"很好，但**缺少自建 HTTP 代理的经典安全清单**，建议补入 §7.5：

| 细节 | 风险 | 建议处理 |
|---|---|---|
| hop-by-hop 头（`Connection`、`TE`、`Transfer-Encoding`、`Keep-Alive` 等） | 请求走私（request smuggling）类漏洞 | 转发前剥离，按 RFC 6143/7230 处理 |
| `Host` / `X-Forwarded-For` / `X-Forwarded-Host` | 下游服务拿到错误的自我认知；伪造来源 IP | core 重写 `Host`，追加（而非信任）`X-Forwarded-*` |
| 请求体大小上限 | 恶意大请求打满 core | 控制面设上限（数据面已走预签名，不经 core） |
| 目标 URL 构造 | SSRF | serviceName 必须命中 `ServiceDiscovery` 已知服务（方案 §7.5 已有"服务不存在→404"，成立，建议写明这是 SSRF 防线） |

这几条不影响架构方向，属于阶段 8 实施前的文档补充项。

### 3.2 档位 1 设计（microservice-phase1-design.md）

**值得肯定**：

| # | 亮点 | 说明 |
|---|---|---|
| 1 | 决策记录规范 | 每个决策带证据、备选方案对比、被拒理由（决策 1 的依赖污染论证、决策 2 的三方案对比、决策 3 的替代路径）——这是架构决策记录（ADR）的正确写法 |
| 2 | SPI 契约取舍有论证 | POJO 而非接口（序列化复杂度）、不设 `renew()`（分层正确性）、`register()` 同时收 definition + instance（职责划分）——三个取舍都成立 |
| 3 | 已知局限如实记录 | cluster provider 只能服务单一服务名，明说"这正是 Nacos 存在的意义"——把局限转化为教学素材，诚实且聪明 |
| 4 | 验证标准可测且诚实 | "启动成功不是通过标准"贯穿全篇；完成标准逐条可勾选 |
| 5 | AGENTS.md 合规内建 | 三配置文件同步、无 `{}` 占位符、`@RolesAllowed`、`@RequestParam`、改 pom 必用 `mvn`、不生成测试——全部对齐 |

**存疑或待补**：

1. **namespace/group 的收敛约定是隐式的**：`ServiceDefinition` 携带 `namespace`/`group`（注册方声明），但 `ServiceDiscovery` 查询接口只收 `serviceName`——发现侧只能用插件自身配置的 namespace/group 查询。也就是说，跨服务可见性依赖"所有服务注册到同一 namespace/group"的**部署约定**，文档没有写明。阶段 4 的 demo 服务与 core 配置不一致时会出现"注册成功但互相看不见"的困惑，建议在 §4 或 §7 明确这条约定。
2. `ServiceRegistryInitializer` 的**生命周期时机**未指定：注册时需要对外端口，而端口确定时机（配置读取 vs web 容器启动后）决定该用哪个钩子。属于实施细节，建议实施时确认（复用 `getSelf()` 逻辑大概率规避了此问题）。
3. Step 4 的 YAML 示例把 `sys.service.nacos.*` 与通用项一起放进三个配置文件，与决策 3"nacos 参数归属插件"在时间线上略有错位（插件此时尚不存在）。无实际危害（键无人绑定时惰性存在），但按决策 3 的精神，nacos 子块更应出现在阶段 3 的实施清单里而非 Step 4。

**存疑或待补**（除 §0 已列的 4 条主项外）：

1. `manifest` 以 `@AllowAnonymous` 暴露**服务拓扑**（服务名、版本、入口路径）给匿名访问者。与 `autoLoad.js` 既有行为一致，局域网产品可接受，但这是**应该有意识接受**的决定，建议文档补一句权衡说明（或加开关）。
2. 代理对 `static/**` 的特殊规则是隐含的：§6.1 静态资源直接映射 `/static/**`（不带 `sfc.api.prefix`），§7.1 接口转发则拼 `sfc.api.prefix`——两条规则不对称但成立，建议在实施时写一张显式的路径映射规则表。
3. 内部令牌（`X-Sfc-Internal-Token`）的校验失败语义（微服务返回 401/403？还是 core 统一处理？）未写明，阶段 8 实施时需定。
