## 2. 专项评审：是否引入独立 Gateway 组件 → **已决策：引入（`microservices/sfc-gateway`）**

### 2.1 决策与职责划分

**结论**：代理职责从 `sfc-core` 内部移出，改为**独立进程的 Spring Cloud Gateway**（Server WebFlux），并由它担任**整站唯一入口**——浏览器只与网关同源对话。完整设计见[网关独立化设计](../microservice-gateway-design.md)。

| 承担者 | 覆盖职责 |
|---|---|
| **`sfc-gateway`（独立进程）** | 入口透传（SPA / `/api/**` / WebSocket）、控制面与静态资源反向代理、**用户凭证的本地验签**、全部代理判定（路径 / 服务白名单 / 自我转发阻断 / api 前缀）、流式管道、负载均衡（`lb://`）、故障重试、400/403/404/503 语义（413 仅作**框架层 413 的归一化**——网关不管控请求体大小）、头部治理（身份头 / 凭证透传 / hop-by-hop / `Host` / `X-Forwarded-*`） |
| **`sfc-core`（业务 ＋ 会话签发）** | 凭证签发与自己的 API 的完整校验（含 Redis 会话白名单）、既有 `@UID` / `@ValidPath` / `@RolesAllowed` **零改动**；⚠️ **不参与代理链路** |
| **微服务自身** | 静态资源 `GET /static/**`；**信任 `X-Sfc-Uid`**（框架期）；可用透传的凭证原值自行完整校验；不得打印凭证 |
| **Nginx（可选，阶段 9）** | 数据面 `/dl/{service}/**` 直连路由 —— 该阶段**已暂缓** |

### 2.2 为什么本次决策与"当时不需要"并不矛盾

本报告先前的结论是"当下不需要独立网关"，理由四条：学习价值最大化、部署形态匹配、与既有安全设施共生、避免再开一条依赖冲突战线。**本次触发独立化的不是那四条，而是两个新的理由**：

| 新理由 | 说明 |
|---|---|
| **官方库的稳定性** | 传输层（连接管理、流式管道、头部语义、负载均衡、重试时机）交给官方库，不再自研 |
| **职责分离** | `sfc-core` 是业务单体，不该同时承担网关职责；把网关职责继承进 core 会让两件事互相牵制 |

同时必须如实记录**代价**：所有流量多一跳（含大文件）、网关成为可用性单点、**密钥一致性成为一条人工运维边**（core 的 `sys.safe.token` ↔ 网关的 `SFC_JWT_SECRET`，且网关不感知在线变更）、版本矩阵分叉（网关 Boot 4.0.8 / core 4.1.0；**该分叉已于 2026-10 随宿主对齐 4.0.8 而消除**）。详见[网关设计 §2](../microservice-gateway-design.md)。

### 2.3 既有论证中仍然成立与发生变化的条目

| 原论证 | 现状 |
|---|---|
| **与既有安全设施共生** | ✅ **仍然成立且被保留**：核心链路（`/api/**`、SPA、WebSocket）上网关**完全透明**，core 的 `@UID` / `@ValidPath` / `ProtectBlocker` / OIDC 原样生效、零改动 |
| **避免再开一条依赖冲突战线** | ✅ **被正面接受而不是绕开**：网关**不继承 root pom、零咸鱼云依赖**，与插件类加载器体系完全隔离（⚠️ 现状校正：它**已在** root `<modules>` 中被聚合——见[技术债务清单](../todo.md) 第 14 条；这影响构建耦合，不影响"零咸鱼云依赖"这条硬标准） |
| 手写代理才能学到的那些点（流式、实例选择、信任边界） | ⚠️ **部分让渡**：改为通过"设计 ＋ 实测验收"习得（[网关设计 · 决策 5 / §6](../microservice-gateway-design.md)） |
| 原"未来引入独立网关的触发条件"（多副本需 LB、限流熔断、多团队、TLS 终结） | ⚠️ 四条**都还没发生**；本次由上述两个新理由触发 |
| 原"与鉴权机制共生"的论证 | ❌ **随之作废**：服务间鉴权已整体后置（信任模式），本报告涉及令牌 / JWKS / `scope` 的条目一并不再适用 |

### 2.4 代理层的必修安全项（清单仍然有效，归属改为网关）

选择自建代理 = 选择自己承担网关的安全细节。以下清单**不会因为换成官方库而消失**——官方库只覆盖传输机制：

| 细节 | 风险 | 处理（**在网关侧**） |
|---|---|---|
| **入站身份头 `X-Sfc-*`** | **任何人都能伪造 uid**（框架期信任模式下最严重的一条） | 转发前**全部剥离**，只注入网关**本地验签**得到的 `X-Sfc-Uid` |
| 会话凭证（`Token` 头 / `token` cookie / `?Token=`） | 30 天长效用户凭证进入微服务及其 access log | ⚠️ **2026-10-11 改判**：由"三入口全部剥离"改为"**原值透传**"——下游需要凭证原值才能做含会话白名单的完整校验；代价是微服务**不得打印凭证**（部署硬约束）。理由见[设计决策 3.3](../microservice-gateway-design.md) |
| 网关侧的验签密钥 | 密钥漂移 ⇒ `/api/ext/**` 全量 403/7005 | `SFC_JWT_SECRET` 环境变量注入 ＋ 启动期 fail-fast；不写默认值、不进代码库 |
| hop-by-hop 头（`Connection`、`TE`、`Transfer-Encoding`、`Keep-Alive` 等） | 请求走私（request smuggling）类漏洞 | 转发前剥离，按 RFC 7230 处理 |
| `Host` / `X-Forwarded-For` / `X-Forwarded-Host` | 下游服务拿到错误的自我认知；伪造来源 IP | 网关重写 `Host`，**覆盖式**写入 `X-Forwarded-*`（丢弃入站值） |
| 请求体大小上限 | 恶意大请求打满入口 | 控制面设上限（数据面走预签名，不过网关） |
| 目标 URL 构造 | **SSRF** | `serviceName` **必须**命中 `ServiceDiscovery` 已知服务，且不得是 `sfc-core` / 网关自身 |

> ⚠️ **信任边界随拓扑迁移**：`sfc-core` 不再是"最外层"，**网关是**。文档与实现中所有"core 是最外层信任边界"的表述都必须随之改写，否则比代码更危险。

**存疑或待补**：

1. **namespace/group 的收敛约定是隐式的**：`ServiceDefinition` 携带 `namespace`/`group`（注册方声明），但 `ServiceDiscovery` 查询接口只收 `serviceName`——发现侧只能用插件自身配置的 namespace/group 查询。也就是说，跨服务可见性依赖"所有服务注册到同一 namespace/group"的**部署约定**，文档没有写明。阶段 4 的 demo 服务与 core 配置不一致时会出现"注册成功但互相看不见"的困惑，建议在 §4 或 §7 明确这条约定。
2. `ServiceRegistryInitializer` 的**生命周期时机**未指定：注册时需要对外端口，而端口确定时机（配置读取 vs web 容器启动后）决定该用哪个钩子。属于实施细节，建议实施时确认（复用 `getSelf()` 逻辑大概率规避了此问题）。
3. Step 4 的 YAML 示例把 `sys.service.nacos.*` 与通用项一起放进三个配置文件，与决策 3"nacos 参数归属插件"在时间线上略有错位（插件此时尚不存在）。无实际危害（键无人绑定时惰性存在），但按决策 3 的精神，nacos 子块更应出现在阶段 3 的实施清单里而非 Step 4。
