## 1. 目标与范围

### 目标

1. **`sfc-core` 不再承担任何 HTTP 转发职责，也不再承担任何代理判定职责**：它只做业务与"会话权威"（签发/校验凭证、Redis 白名单），**不参与代理链路**
2. 新建独立进程 `microservices/sfc-gateway`（Spring Cloud Gateway **Server WebFlux**），作为**整站唯一入口**：浏览器只与它同源对话
3. 微服务流量的**传输层**（路由、负载均衡、重试、流式管道、头部治理）交给官方库，不再自研
4. **用户凭证由网关自己验签**（密钥经环境变量注入），判定结果注入 `X-Sfc-Uid`；**凭证原值原样透传**给下游，供下游做自己的完整校验

### 明确不做

| 不做 | 原因 |
|---|---|
| 拆分 `sfc-core` 的业务 | 非目标。core 仍是单体业务应用，只是不再兼职网关 |
| **服务间调用鉴权**（令牌 / JWKS / `aud` / `scope`） | **整体后置**（阶段 5）。框架期采用信任模式；安全机制另行规划，问题清单见[路线图阶段 5](microservice-roadmap.md) |
| **密钥的分发与轮换机制** | 网关只读启动时的环境变量：core 支持在线改密钥，网关**不感知、不热更新**；两侧一致性由部署保证（见决策 3.4 与技术债务清单） |
| 在网关侧校验 Redis 会话白名单（登出 / 改密即时失效） | 网关只做"验签 ＋ 过期"；完整校验由持有凭证原值的下游完成。取舍见决策 3.3 |
| 限流 / 熔断 / 链路追踪 | 治理能力。SCG 的官方 filter 使它们**随时可加**，但本阶段引入会扩大验收面 |
| 微服务之间的相互调用 | 属档位 2（阶段 6） |
| 数据面预签名直连 | 属阶段 9，**已暂缓**（信任模式下 URL 载体没有安全语义）。框架期下载走网关流式代理 |
| 阶段 7 的扩展清单与静态资源代理 | 属阶段 7。网关**只预留路由位，不提前放行前缀**（决策 7） |
| 把网关做成 Nacos 里的"服务"来被调用 | 网关是入口，不被任何服务反向调用；它只注册自身以便在管理端可见 |

## 2. 为什么独立：三个问题、三条代价、一份债务

用户提出的三个诉求，如实分项回答（**不夸大**）：

| 维度 | 结论 | 依据 |
|---|---|---|
| **更清晰的项目结构** | ✅ **有条件成立** | 清晰来自"**独立进程 ＋ 边界重划**"（core = 控制面策略与判定；网关 = 数据面传输），而不是来自换库。若把 SCG 以依赖形式内嵌进 core，结构一点没变，只是把自研转发器换成官方转发器 |
| **更强的扩展性** | ✅ **成立** | 路由配置化；限流（`RequestRateLimiter`）、熔断（`CircuitBreaker`）、重试、可观测（actuator / metrics）、动态路由都是官方现成件。自研转发器每加一项能力都是一段新代码 |
| **更好的稳定性** | ⚠️ **部分成立（必须说清）** | 官方库覆盖的是 **HTTP 传输机制**（连接管理、流式管道、头部语义、负载均衡、重试时机）。而**真正容易出事的是策略**（身份头剥离、凭证剥离、`X-Forwarded-*` 覆盖、hop-by-hop 剥离、自我转发阻断、路径"只拒绝不规范化"、带请求体不重试）——**一条都不在 SCG 的职责里**，仍要自己写 filter。准确表述是"**传输层不再是自己写的代码**"，不是"转发逻辑变成配置" |

**三条代价**（显式接受）：

| # | 代价 | 说明与对策 |
|---|---|---|
| 1 | **所有流量多一跳** | 含 SPA 静态资源、1GB 下载、大文件上传。8.1 预研必须给出吞吐对照 |
| 2 | **网关成为可用性单点** | 网关挂 = 整站不可用。入口切换（8.6）前保留"浏览器直连 core:8087"的回退路径 |
| 3 | **密钥一致性成为一条人工运维边 ＋ 版本矩阵分叉** | 网关的验签密钥来自环境变量，core 的密钥存在数据库配置项 `sys.safe.token`（首次启动随机生成、且支持在线修改）⇒ **两侧一致只能靠部署保证**，且网关不感知在线变更；版本上网关用 Boot 4.0.8，core 用 Boot 4.1.0，两者只通过 HTTP 协议耦合、**不共享任何 jar**（8.8 起连 HTTP 调用都没有了：core 不再出现在代理链路上） |

**一份安全债务（框架期必须显式记账）**：

| # | 债务 | 到期条件 |
|---|---|---|
| 1 | 微服务只信任明文头 `X-Sfc-Uid`：**任何能直连微服务端口的人都能伪造任意用户** | 安全阶段（阶段 5）换成**可验证**的载体 |
| 2 | microservice 侧**没有任何权限校验**；core 的 `/api/internal/**` 同样无服务身份校验 | 同上 |
| 3 | **网关不校验会话白名单**：登出 / 改密 / 踢下线后旧凭证在网关侧仍算"已认证"，完整校验只能由拿到凭证原值的下游完成 | 安全阶段；或给网关加 Redis 依赖（本轮明确不做） |
| 4 | **网关不感知密钥在线变更**：core 改完 `sys.safe.token` 后必须重启网关并重新注入环境变量，否则全量 `403/7005` | 同 5（密钥分发与轮换机制） |
| 5 | **凭证原值透传给微服务**：30 天长效凭证会进入微服务及其 access log | 安全阶段换成短时、受众绑定的载体 |
| 6 | 预签名直连（阶段 9）**暂缓**——没有可验证载体时，URL 里的"凭证"没有意义 | 随安全阶段一起做 |

> **硬约束**：**微服务与 core 的内部接口只允许内网 / 本机可达，网关是唯一对外入口；上公网前必须先完成阶段 5。**

> **与[方案评估报告 §2](review/microservice-plan-review.md) 的关系**：该报告当时判定"当下不需要独立网关"，触发条件是四条（多副本需前置 LB、限流熔断、多团队、TLS 终结）。本次触发它的**不是**那四条，而是"官方库稳定性 ＋ 职责分离"。报告 §2 已按本文件更新，其余论证仍成立。

## 3. 拓扑

```
                              浏览器（同源：只跟网关说话）
                                          │
                        ┌─────────────────▼──────────────────┐
                        │        sfc-gateway :8081           │
                        │  Spring Cloud Gateway 5.0 (WebFlux)│
                        │  · 本地验签（密钥←环境变量）           │
                        │  · 本地策略：路径 / 白名单 / 前缀 / 回环 │
                        │  · 不签发凭证、不查会话白名单           │
                        └──┬──────────────────────────────┬──┘
   ①/②/③ 透传（含 WebSocket）│      ④ /api/ext/{svc}/**       │  (不再调用 core 判定)
                        │      验签 → 判定 → 注入 → 改道   │
                        ▼                              ▼
        ┌───────────────────────────────┐   ┌──────────────────────────────┐
        │        sfc-core :8087         │   │  微服务（独立进程）             │
        │  会话权威（JWT 签发 ＋ Redis    │   │  lb://{serviceName}          │
        │  白名单）＋ 既有安全设施         │   │  信任 X-Sfc-Uid ← 网关注入      │
        │  @UID @ValidPath @RolesAllowed│   │  凭证原值同样透传到本层          │
        │  （**零改动**，不参与代理链路）   │   └──────────────────────────────┘
        └───────────────┬───────────────┘
                        │ 注册 / 心跳 / 发现（Nacos，group SFC；网关用它做白名单与实例选择）
                        ▼
        ┌──────────────────────────────────────────────────────────────┐
        │  密钥一致性（人工运维边）：core 的 sys.safe.token  ──▶ 环境变量    │
        │  SFC_JWT_SECRET（网关启动时读取，不热更新）                       │
        └──────────────────────────────────────────────────────────────┘
```

**五条链路**

| # | 链路 | 谁处理 | 鉴权 |
|---|---|---|---|
| ① | `/`、`/index.*`、`/assets/**`、`/static/**`、`/ext/**`、`/oauth*`、**`/oauth2/**`、`/.well-known/**`、`/connect/**`** → core | 网关透明透传 | 由 **core** 自己判（网关不参与） |
| ② | `/api/**`（core 业务 API）→ core | 网关透明透传 | 由 **core** 自己判（网关不参与） |
| ③ | WebSocket：`/api/ws`、`/api/ai/wschat`、`/api/webrtc/ws/*`、`/api/webshell/*` → core | 网关透传 upgrade | 由 core 自己判 |
| ④ | `/api/ext/{serviceName}/**` → 微服务 | **网关**：本地验签 → 本地策略 → 注入 `X-Sfc-Uid` → `lb://` 转发 | 网关本地验签（密钥来自环境变量）；凭证原值透传下游 |
| ⑤ | 阶段 7 的清单与静态资源 | 清单透传到 core；静态直连微服务 | 匿名（静态需路径校验） |

> **已删除的链路**：`POST /api/gateway/resolve`（网关 → core 的"控制面查询"）。自 8.8 起 core 不参与代理链路：**验签与判定都在网关进程内完成**，core 侧该端点、策略服务、DTO 与错误码枚举已一并删除。

**关键性质**：链路 ①②③ 上，网关是**完全透明**的——不解析身份、不注入身份头、不改写业务语义。因此 core 的 `@UID` / `@ValidPath` / `ProtectBlocker` / OIDC 全部**原样生效、零改动**，"信任边界连续"这一条没有因为引入网关而丢。

> ⚠️ **OIDC 前缀必须显式列出**（预研的第一次踩坑）：内置授权服务器的端点在 `/oauth2/**`、`/.well-known/**`、`/connect/**`，**不在 `/api` 下**。漏掉它们时同一请求会"直连 core 403、经网关 404"，授权码流程、设备码流程、discovery 文档与退出端点会整体失效。前端的 vite dev proxy 代理的正是 `/api`、`/oauth`、`/oauth2`、`/.well-known/openid-configuration` 这四个前缀，可作对照。

## 4. 决策记录

### 决策 1：网关形态 → **SCG Server WebFlux**（`spring-cloud-starter-gateway-server-webflux`）

| 变体 | 结论 | 理由 |
|---|---|---|
| **Server WebFlux（采用）** | ✅ | 唯一入口必须转发 WebSocket（链路 ③ 有 4 个 WS 端点），而[官方文档](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webmvc/how-it-works.html)中 MVC 变体**没有 WebSocket 转发能力**；WebFlux 是 SCG 主线，过滤器生态最全；流式（Netty）是默认行为，正好命中"禁止 `byte[]` 全量缓冲"的硬约束 |
| Server WebMVC | ❌ | Servlet / WebMvc.fn 模型与项目一致、上手成本低，但**不支持 WebSocket 转发** ⇒ 在本拓扑下直接不可用 |
| Proxy Exchange（`spring-cloud-gateway-proxyexchange-webmvc`） | ❌ | 它是 `ProxyExchange<byte[]>` 的注解式用法，与"必须流式、禁止全量缓冲"的硬约束冲突 |

> **reactive 栈的隔离性**：WebFlux / Reactor 只存在于网关进程内，`sfc-core` 仍是纯 Servlet 单体。这是"独立进程"顺带换来的好处——两套编程模型互不污染。

### 决策 2：工程位置与版本边界 → **`microservices/sfc-gateway`，独立 POM 边界**

| 项 | 取值 | 依据 |
|---|---|---|
| 位置 | `microservices/sfc-gateway` | 与 [microservices/README.md](../../../microservices/README.md) 的约定一致：仓库内统一维护、独立构建独立运行 |
| 父 POM | `spring-boot-starter-parent:4.0.8`，**不继承 root pom** | 继承 root pom 会被拖入约 208 个 jar（决策见[档位 1 设计 §5 决策 1](microservice-phase1-design.md)）。⚠️ **现状校正（2026-10-11）**：本工程**当前在** root `<modules>` 中（根目录一次 `mvn package` 即可产出全部产物），但"不继承 root pom ＋ 零咸鱼云依赖"这两条硬标准仍然成立；代价是"改微服务要重建宿主"的耦合回来了 |
| Spring Boot | **4.0.8** | 与 `sfc-demo-service` 同版本 |
| Spring Cloud | **2025.1.0**（Oakwood） | 官方矩阵基线 `spring-boot.version = 4.0.0`；对应 SCG **5.0.0** |
| Spring Cloud Alibaba | **2025.1.0.0** | 提供 `nacos-discovery` starter（`lb://` 的服务实例来源） |
| 咸鱼云依赖 | **零** | 沿用 demo 的验证方式：`mvn dependency:list` 中 `com.xiaotao` / `sfc-*` 命中 0 条 |

> **一处既存偏差（已按现状校正）**：`microservices/` 下的 `sfc-demo-service` 与 `sfc-gateway` **当前都出现在 root pom 的 `<modules>` 里**，与 [microservices/README.md](../../../microservices/README.md) 早先声明的"不进 root `<modules>`"不符。两条"独立"硬标准（**不继承 root pom**、**零咸鱼云依赖**）仍然成立，因此本设计按现状维持；是否从 `<modules>` 移除属于构建策略选择，已记入[技术债务清单](../todo.md) 第 14 条。

### 决策 3：身份传递 → **网关本地验签 ＋ 明文头注入 ＋ 凭证原值透传**

网关**不签发凭证**，但**持有验签密钥**（环境变量注入）：它在自己进程内验证用户凭证（签名 ＋ 过期），
取出 uid 注入明文身份头，并把**凭证原值原样透传**给目标微服务。

#### 决策 3.1：删除了 resolve 端点（原线协议）

原实现是一条"控制面查询"：

```
POST /api/gateway/resolve?keep=1                  ← 网关 → core：这是谁、转到哪
  用户会话凭证：Token 头 / token cookie / ?Token=
  200 → { uid, serviceName, targetPath }          ← core 判定，网关只做映射
```

**该端点已整体删除**（core 侧 `GatewayResolveController` / `GatewayResolveService` / `GatewayResolveProperties` /
`GatewayResolveParam` / `GatewayResolveVo` / `GatewayError` 一并移除），
因为"每次代理请求都要问一次 core"与"网关持有唯一身份来源"这两件事已经不能同时成立：

1. 只要还调 resolve，**凭证就仍然要交给 core 判定**——这正是本次要消除的依赖；
2. 判定本身（路径规则 / 服务白名单 / 前缀解析）并不需要 core 的任何领域知识，**网关自己就能做**
   （服务发现它本来就有，因为 `lb://` 就靠它）；
3. 少一次内网往返，少一条信任边，少一份"core 不可达 ⇒ 全站代理不可用"的耦合。

现行为（全部在网关进程内）：

```
① 取凭证：Token 头 → ?Token= → token cookie（顺序与 core 的 SecureUtils.getToken 一致）
② 验签：Jwts.parser().verifyWith(Keys.hmacShaKeyFor(SFC_JWT_SECRET)).parseSignedClaims(token)
        → data 声明的 JSON 里取 id ⇒ uid；失败/过期 → 403/7005
③ 判定：方法白名单 → 路径(只拒绝不规范化) → 服务名 → 自我转发阻断 → 实例列表 → sfc.api.prefix
        → targetPath；失败 → 400/7000 或 404/7001（注册中心不可用为 503/7004）
④ 注入：X-Sfc-Uid = uid（值只来自②）；凭证三入口【不改写】，原样透传
⑤ 改道：lb://{serviceName}{targetPath}{?原查询串} → 官方负载均衡 filter
```

| 失败情形 | HTTP | 业务码 | 产出方 |
|---|---|---|---|
| 凭证缺失 / 验签失败 / 已过期 | 403 | 7005 | 网关（本地验签） |
| 路径或方法非法（见决策 4） | 400 | 7000 | 网关（本地判定） |
| 服务未注册 / 无健康实例 / **目标为 core 或网关自身** | 404 | 7001 | 网关（本地判定） |
| 注册中心不可用 | 503 | 7004 | 网关 |
| 实例在册但连不通（重试耗尽） | 503 | 7004 | 网关（转发阶段） |

> **契约不变**：错误体仍是 `{code, data:null, msg, businessCode}`（与 core 其他接口同形），
> 所以前端零改动。**7002（代理功能未启用）已从契约中删除**——它原先是 core 的
> `sys.service.gateway.enabled` 的语义，该配置随 resolve 一起移除：代理能力现在完全由网关掌握，
> 不存在"网关在、代理却被 core 关掉"这一形态。

#### 决策 3.2：为什么不再让 core 验会话（与原决策的改判）

原决策曾**明确否决**"网关自己验会话"，理由是：①必须与 core 共享用户 JWT 密钥，等于把会话签发能力复制给第二个进程；②会话校验栈被复制成两份，任何一侧改动都可能造成"网关放行、core 拒绝"的不一致。

**这两个理由今天依然成立，改判的是"代价与收益的权衡"**——因为需求侧的目标变了：

| 维度 | 原方案（core 验会话） | 现方案（网关验签） |
|---|---|---|
| 与 core 的耦合 | 每次代理请求一次 resolve 调用；core 不可达 ⇒ 代理不可用 | **零 HTTP 调用**；core 只按自己的业务需要运行 |
| 目标路径的产出 | core 算好回传 | 网关自己算（判定与转发天然同一字符串） |
| 错误语义 | core 产生、网关映射 | 网关产生（形态契约不变） |
| 密钥 | 网关不持有 | **网关持有**（环境变量）；密钥轮换与一致性成为运维责任 |
| 会话栈重复 | 只有 core 一份 | 判定口径**刻意与 core 同一 API、同一版本**（`Keys.hmacShaKeyFor` ＋ `verifyWith`，算法随密钥长度自适应，不写死 HS256）；不一致的风险用"逐条对齐 ＋ 验收项"控制 |

**仍然不做**的三件事（有意为之，已记账）：
1. **不查 Redis 会话白名单**（登出 / 改密即时失效）——完整校验交给拿到凭证原值的下游；
2. **不感知密钥在线变更**——core 支持在线改 `sys.safe.token`，网关只读启动时的环境变量；
3. **不做 `aud` / `scope` / 服务间鉴权**——那是阶段 5 的题目。

> ⚠️ **"当时否决、现在改判"要留下理由**：否则后来者只看到结论，会以为两个决策里必有一个是错的。
> 这里的真实变化是**需求**（不再允许"验证凭证必须问 core"），而不是原论证被推翻。

#### 决策 3.3：三个凭证入口 → **读取用于验签，原值透传给下游**

| 入口 | 现状 |
|---|---|
| `Token` 请求头 | 网关验签取值的第一优先级；**原值透传** |
| `?Token=` 查询参数 | 第二优先级；**原值透传**（`/api/ws` 这类握手场景的唯一入口，剥离即打死） |
| `token` Cookie | 第三优先级；**原值透传**（其余 Cookie 同样原样保留） |

**改判理由（这是本次最容易被误读的一条）**：原实现把三个入口全部剥离，判据是"微服务不该拿到通往 core 的钥匙"。
现在的判据是**校验责任的划分**：网关只做"验签 ＋ 过期"，而**完整**校验（含会话白名单）只有拿到凭证原值的下游才能做。
两害相权：

| 选择 | 收益 | 代价 |
|---|---|---|
| 剥离（原） | 凭证不外泄到微服务 | 下游**只能**信任明文 `X-Sfc-Uid`；登出后的凭证在整条链路上都算有效 |
| 透传（现） | 下游可以自己完成完整校验；"凭证原值"是唯一可验证的载体 | 长效凭证进入微服务及其 access log ⇒ **部署侧硬约束：微服务不得打印凭证** |

> 顺序必须与 core 的 `SecureUtils.getToken` **完全一致**（头 → 参数 → Cookie），且只取一个值：
> 否则会出现"网关按 A 判通过、core 按 B 判失败"，症状是"网关放行、下游 403"。
> 同名 Cookie 重复时两侧都取**最后一个**（core 的循环是覆盖式写入，不 break）。

#### 决策 3.4：`X-Sfc-Uid` 的唯一注入点

| 规则 | 说明 |
|---|---|
| 网关**剥离入站的一切 `X-Sfc-*`**，然后写入自己的 `X-Sfc-Uid` | 这是信任模式的**唯一防线**：不剥离就等于"谁都能当任意用户" |
| ⚠️ **剥离对所有路由生效，注入只对代理分支生效** | 剥离不加路由条件，是为了让**浏览器流量结构上不可能**携带该头——core 的内部接口（阶段 6 的 `/api/internal/**`）会**信任**这个头，若只剥离代理分支，`/api/**` 透传链路就成了伪造身份的通道。剥离子集不含任何业务语义（只删除、不注入），因此 core 透传链路"完全透明"的性质不受影响 |
| 值只能来自**网关的本地验签结果** | 网关**不得**从任何请求参数 / 头 / 路径里取 uid；也不接受调用方自带的同名头（已被剥离） |
| 头名常量**两侧各自声明**（网关侧 `SfcTrustHeaders`） | 网关与微服务都遵循"零咸鱼云依赖"，谁都引用不到 `sfc-cloud-api`。因此契约由**文档**承载，两侧常量文案互相指向 |
| 微服务侧**不做任何校验**（有意为之） | 债务与到期条件见 §2 |

#### 决策 3.5：密钥的来源与一致性（运维契约）

| 项 | 约定 |
|---|---|
| core 侧 | **零改动**：密钥仍在数据库配置项 `sys.safe.token`（首次启动随机生成，支持在线修改） |
| 网关侧 | 环境变量 **`SFC_JWT_SECRET`**（yml 写作 `sfc.gateway.jwt-secret: ${SFC_JWT_SECRET:}`），**无硬编码默认值** |
| 取法 | 从 core 的配置表 `config`（`item_key='sys.safe.token'` 的 `item_value`）或管理端配置页取出，注入容器 / 启动脚本 / IDE 运行配置 |
| 启动校验 | 缺失或 UTF-8 长度 < 32 字节 ⇒ **启动失败**（fail-fast）。否则症状会是"网关照常起来、但所有 `/api/ext/**` 一律 403/7005" |
| 漂移症状 | 登录正常（core 自己签的），但经网关访问微服务全量 `403/7005` ⇒ 先核对两侧密钥是否一致 |
| 变更 | 改完 core 的密钥后**必须重启网关**并重新注入；网关不做热更新（见[技术债务清单](../todo.md)） |

### 决策 4：职责划分 → **判定与转发都在网关，core 不参与代理链路**

| 关注点 | 归属 | 说明 |
|---|---|---|
| 会话有效性、`uid` | **网关** | 本地验签（`GatewayTokenVerifier`）：与 core 同一 API、同一密钥、同一过期语义；**不查 Redis 白名单**（见决策 3.2） |
| 路径合法性（**只拒绝、不规范化**） | **网关** | 判定与转发用同一个字符串。拒绝清单：编码的斜杠 / 反斜杠 / NUL / 点 / 空格与控制字符、**重复斜杠 `//`**、`.` `..` 路径段、非法百分号转义、不支持的方法、超长路径。⚠️ `//` 是预研实测补进来的：网关（Netty）会把 `//` 折叠后再转发，不拒绝就必然出现"判定用 A、转发用 B" |
| 服务名白名单（SSRF 防线） | **网关** | 只信注册中心（Spring Cloud `DiscoveryClient`，即 `lb://` 的同一份发现结果）；目标为 core / 网关自身一律 404 |
| API 前缀解析与 `targetPath` 拼接 | **网关** | 实例 metadata 的 `sfc.api.prefix` → 配置缺省 `sfc.gateway.default-api-prefix`；非法前缀**不静默回退** |
| **用户凭证的签发** | **core**（唯一签发方） | `JwtUtils` / `TokenService` / `SysSafeConfigConfiguration` **零改动** |
| **用户凭证的完整校验**（含会话白名单） | **core**（对到达它自己的请求）与**下游**（用透传的凭证原值自行校验） | 网关只验签 ＋ 过期，**不**校验白名单 |
| 路由、负载均衡、超时、重试 | **网关** | SCG `lb://` ＋ 官方 filter |
| 流式管道（请求 / 响应两个方向） | **网关** | Netty 默认行为 |
| 头部治理（身份头、凭证、hop-by-hop、`Host`、`X-Forwarded-*`） | **网关** | 见决策 5（凭证只读不剥离） |
| 请求体大小上限 | **不做**（既不是网关、也不是 core） | 网关只做**流式通道**：不缓冲、不计数、不截断。请求体多大由承载业务的服务自己决定（core 的 multipart 上限是 8GB）。要限流/防打满，用专业边缘（nginx / Ingress / WAF）——那是它们的本职，网关不重复实现（决策 5 第 8 条） |
| 对外的错误语义（7000 / 7001 / 7004 / 7005） | **网关**（唯一产出方） | 契约不变、形态与 core 其他接口同形；7002 已从契约删除 |

> **分工原则一句话**：**"能不能转"与"怎么转"都由网关做，core 只管自己的业务与凭证签发。**
> 网关是唯一持有验签密钥的入口进程——它被攻破不等于 core 被攻破（但**微服务被攻破就是任意用户**，这是框架期债务 1）。

### 决策 5：网关侧必须自实现的 filter（SCG 不代劳的部分）

下表即落地清单（"实现点"列为真实类名，均在 `microservices/sfc-gateway` 内）：

| # | 规则 | 实现点 |
|---|---|---|
| 1 | **剥离入站一切 `X-Sfc-*` 身份头**（**所有路由**） | `TrustHeaderSanitizeFilter`（order -99；**信任模式的唯一防线**） |
| 2 | 本地验签取 uid，注入 `X-Sfc-Uid` | `GatewayTokenVerifier` ＋ `TokenExtractor` ＋ `ProxyRequestFilter`（order 10100，与 4~6、13 同一次请求变更） |
| 3 | 凭证三入口**原样透传**（`Token` 头 / `?Token=` / `token` Cookie） | 同上：**只读取，不改写、不剥离**（行为已按决策 3.3 反转） |
| 4 | 本地策略判定：方法 / 路径 / 服务名 / 自我转发阻断 / 实例列表 / API 前缀 | `ProxyPolicyService`（实例查询调度到 `boundedElastic`，与 `lb://` 同源但不走 LB 缓存） |
| 5 | 判定失败的对外语义（400/7000、404/7001、403/7005） | `ProxyRejectException` ＋ `ProxyRequestFilter`（写成与 core 同形的错误体） |
| 6 | hop-by-hop 头剥离、`Host` 重写 | **SCG / Reactor Netty 默认行为**——已实测确认（下游看不到 `TE` / `Connection` / `Transfer-Encoding`；`Host` 为实例地址） |
| 7 | `X-Forwarded-For` / `-Host` / `-Proto` / `-Port` **覆盖式**写入，并一并覆盖 `X-Real-IP` | `XForwardedOverrideFilter`（order -100；`X-Real-IP` 是 core 的 `remote-ip-header` 认的头，不覆盖它则来源 IP 一律变成网关地址） |
| 8 | ~~请求体上限~~ → **决策：不做**（网关不管控请求体大小） | **无实现点**。预研实测已证明"做得到"（自定义增量拦截能让 chunked 也变 413），但**能力上做得到 ≠ 职责上该做**：网关一旦开始计数/拦截，就要在唯一入口上维护一套与业务无关的体量策略，还会把"多大算大"的判定权从业务服务手里拿走。原 `ProxyRequestBodyLimitFilter`（order 10020）已删除，`sfc.gateway.max-request-size` 配置项一并移除。⚠️ **这条是明确的非目标，不要再补回来**；挡"大请求打满入口"请用专业边缘（nginx `client_max_body_size` / Ingress / WAF） |
| 9 | 只对 `GET` / `HEAD` 换实例重试 | 路由声明中的官方 `Retry`（`methods=GET,HEAD`）；写请求只打一个实例——请求体是一次性流，带体重试等于让下游收到空请求体而调用方看到"成功" |
| 10 | 连接层陈旧连接自愈 | **不做特殊处理**：实测 75s 空转后池中连接已被对端回收、首个不可重试的 `POST` 仍 200。**不要**关闭客户端库的连接层重试；防重放由"请求体不可重放"独立保证 |
| 11 | 错误语义映射（400 / 403 / 404 / 413 / 503） | `GatewayErrorWebExceptionHandler`（order -2，映射 503/7004；413/7003 仅作**框架层 413 的归一化**——网关自己不产生 413）；判定与验签产生的 400/7000、403/7005、404/7001 由 `ProxyRequestFilter` 自己写成同形态响应 |
| 12 | 密钥的启动期校验（fail-fast） | `GatewayTokenVerifier` 构造器：缺失 / 短于 32 字节 ⇒ 拒绝启动，并在日志里点名 `SFC_JWT_SECRET` |
| 13 | 原始 `rawPath` / `rawQuery` 直接用；**网关不做任何规范化** | `ProxyRequestFilter`（`URI.getRawPath()` / `getRawQuery()`；查询串里的非法构造 → 400/7000，而不是 500） |

> **为什么 2~5、13 合并在同一个 filter 里**：拆开会引入"注入了但还没判定"这类中间态风险（顺序一改就破防）。
> 合成一次 `mutate()` 后，判定结果、身份注入与改道是同一个对象上的原子结果：要么全部生效，要么整条请求不转发。
>
> **顺序必须落在 10000 与 10150 之间**：`RouteToRequestUrlFilter`（10000）先把路由 URI 摊平成请求 URL，本 filter（10100）覆盖它并换成 `lb://{serviceName}{targetPath}`，官方 `ReactiveLoadBalancerClientFilter`（10150）才把 `lb://` 换成真实实例地址。
>
> **路由声明中的 `micro-proxy` 用占位 URI**（`lb://proxy-target-unset`，真实目标由 filter 经 `GATEWAY_REQUEST_URL_ATTR` 覆盖）：刻意不用 `no://op` 这类"安静占位"——万一 filter 未生效，占位服务名解析不到实例会表现为 **503**，而不是"空响应的 200"。**故障要响，不要静默。**

### 决策 6：网关自身的服务注册 → **注册，但不可被代理**

网关启动时以 `sfc-gateway` 服务名注册到 Nacos（group `SFC`，同 demo），目的只是让管理端 `GET /api/admin/sys/service/list` 能看到完整拓扑。

⚠️ **随之而来的两条规则**：

1. **网关自己的判定**必须把"目标服务名 ∈ {`sfc.gateway.core-service`, 网关自身服务名}"一律判 404——否则 `/api/ext/sfc-gateway/**` 会形成回环（这条原先在 core 的 resolve 里，现已随判定一起下沉）；
2. 网关自身不得挂载任何业务端点（除健康检查）。

### 决策 7：阶段 7 / 9 的预留位 → **只留位置，不提前放行**

| 未来链路 | 在网关中的位置 | 本阶段做什么 |
|---|---|---|
| `/api/ext/manifest`（阶段 7） | 透传到 core | 只写路由规则，**不实现** |
| `/api/ext/{svc}/static/**`（阶段 7） | 直连微服务 `/static/**`（**不拼 `sfc.api.prefix`**），匿名 ＋ 路径校验 | 只留路由位。**在静态代理真正实现之前，不得把该前缀加入任何放行规则**——先放行后补校验 = 留出未被消费的攻击面 |
| `/dl/**`（阶段 9） | **⏸ 暂缓**：框架期下载走网关流式代理 | 不写路由 |

### 决策 8：core 侧代理代码的处置 → **core 内不保留任何转发实现，也不保留任何代理判定**

core 的职责是业务与会话签发，**不参与代理链路**：`POST /api/gateway/resolve`、其策略服务（路径校验 / 服务白名单 / 自我转发阻断 / metadata 前缀解析）、配置类、DTO 与错误码枚举**全部已删除**（8.8），`sys.service.gateway.*` 配置节点同步清理（4 个配置文件 ＋ `docs/quick-start/config.md`）。**不要为了"以后再接回来"而保留半套实现**——那只会让后来者以为 core 仍然参与判定。

### 8.1 预研实测（spike，不碰生产代码）✅

> **已完成，结论：方案成立**——完整结果与数字见[**预研实测报告**](microservice-gateway-spike-report.md)。8 项实测中，WebSocket 透传（最高不确定性）通过；**路径保真**改变了实现方案（网关会折叠 `//`，core 侧因此追加"拒绝重复斜杠"）；**请求体上限**则经过两轮收敛：先补了自定义增量拦截，后按决策**改为网关完全不管控**（决策 5 第 8 条）。
>
> **不合格就停在这里**的约定仍然有效：回退成本 = 删掉一个独立工程。

| # | 实测项 | 为什么必须实测 |
|---|---|---|
| 1 | `/api/**` 完整透传（Cookie / `Set-Cookie` / 状态码 / 重定向保真） | 唯一入口的前提 |
| 2 | **WebSocket 透传**（4 个端点全测） | 最高不确定性：先试 `http://` 目标带 `Upgrade` 是否自动升级；若否，为 WS 路径单配 `ws://` / `lb:ws://` 路由 |
| 3 | `lb://sfc-demo-service` ＋ 两个实例的轮询 | 验证 SCA discovery ＋ loadbalancer 的组合 |
| 4 | **流式**：1GB 响应体在 `-Xmx512m` 下不 OOM；8MB 上传 SHA-256 一致 | 硬约束"禁止全量缓冲"的直接验证 |
| 5 | `Retry` 语义：只对 GET/HEAD；**陈旧连接**在 Reactor Netty 下是否自愈 | 决策 5 第 9 / 10 条 |
| 6 | 请求体上限（实测官方 `RequestSize` 不拦 chunked） | 决策 5 第 8 条（**结论：网关不做上限管控**，只保证不截断、不缓冲） |
| 7 | `%2e%2e` / `%2f` / `%20` 等构造的行为，与 core 的 `StrictHttpFirewall` 协同 | 路径保真 |
| 8 | 大文件经网关的吞吐对照 | 代价 1 的量化 |

> **不合格就停在这里**：回退成本 = 删掉一个独立工程。这正符合路线图"每步只引入一个新变量"的原则。

### 8.2 网关工程骨架 ✅

`microservices/sfc-gateway`：`pom.xml`（版本矩阵见决策 2）＋ 启动类 ＋ `application.yml` ＋ 路由 ＋ 健康检查。
落地时有三个"不实测不知道"的坑：SCG 自己有一个 `GatewayProperties` bean（同名即启动失败，已改名 `SfcGatewayProperties`）；Spring Cloud 2025 起 WebFlux 服务端配置前缀迁到 `spring.cloud.gateway.server.webflux.*`；JDK 23+ 不再默认启用注解处理，不写 `<proc>full</proc>` 则 Lombok 静默失效。

### 8.3 ~~core 侧 resolve 端点~~ → **已删除（历史）**

原实现：`controller/GatewayResolveController`（`POST /api/gateway/resolve`）＋ `service/gateway/GatewayResolveService`（策略）＋ `GatewayResolveProperties`（`sys.service.gateway.enabled` / `default-api-prefix`）＋ `GatewayError`（7000~7005）＋ 请求/响应 DTO。

**现状**：以上文件**全部删除**，`sys.service.gateway.*` 配置节点从 4 个配置文件与 `docs/quick-start/config.md` 中清理。判定与错误语义**整体迁移**到网关（见 8.8），因此 core 内不保留任何代理判定代码（决策 8）。保留本节只为记录演进与"当时为什么这么设计"。

### 8.4 网关侧路由与 filter ✅（行为已在 8.8 更新）

按决策 5 的 13 条实现；`/api/ext/**` 路由走"**本地验签 → 本地判定 → 剥离入站身份头 → 注入 `X-Sfc-Uid` → 凭证原样透传 → `lb://` 转发**"。错误语义、业务码、重试规则与[档位 3 §7.7](microservice-phase3-frontend-integration.md) 对齐。

> **历史上 resolve 调用保持"薄"的做法**（`@HttpExchange` 声明式接口 ＋ `lb://{core-service}` ＋ Spring Cloud LoadBalancer）：随 8.8 一起**删除**。这里留一句结论：当时选它而不是 OpenFeign，是因为官方已把 Spring Cloud OpenFeign 标为 feature-complete（只维护）且它是阻塞栈——如果将来又需要网关调用别的服务，仍然优先 `@HttpExchange` ＋ 响应式栈。

### 8.5 信任边界不变式（不可协商）✅

`uid` **只来自网关自己的本地验签**；网关**剥离入站 `X-Sfc-*`**（所有路由）；微服务不读任何名为 `uid` 的参数；篡改 `?uid=999` 的请求必须无效。
**已取证**（预研报告 §3.9）：一条请求同时带 `X-Sfc-Uid: 999`、伪造 `X-Forwarded-For/Proto`、`TE`，下游只看到真实 uid 与网关观测到的转发头。
⚠️ 取证中的"凭证三入口全部消失"一条**已随 8.8 反转**：现在凭证三入口**原样到达**下游（见 8.8 的新取证）。

### 8.6 入口切换（浏览器只访问网关）✅（HTTP 级）/ ⏳（浏览器点击级）

core 侧需要一并确认：`server.forward-headers-strategy`（网关在 core 前面，绝对 URL 与重定向要正确）、OIDC 重定向地址、Cookie 域与端口行为；网关侧需要确认：超时、上传大小不得截断（multipart 上限仍在 core）。

**实测结论**：**core 侧无需改动** —— OIDC discovery 会自动随入口宣告（经网关 `issuer=http://127.0.0.1:8081`、直连 `:8087`），Cookie 与静态资源逐字节一致，multipart `PUT` 上传经网关与直连行为一致；网关**不设任何请求体上限**（决策 5 第 8 条），core 的 8GB 上传原样通过。
**HTTP 级已闭合**：13 个用例经网关与直连状态码/字节数/SHA-256 全一致；`/api/ws` 握手；OIDC 端点与 discovery 走位；死实例在**判定视图**里 1 秒内消失（404/7001），在册但连不通时为 503/7004 ⇒ **判定侧的实例列表没有加自己的缓存**。
**留给浏览器**：登录、上传/下载、播放、WebSocket 通知、插件页面与（若启用）OIDC 授权码流程的点击级回归。

### 8.7 收尾 ✅

确认 core 内无任何转发实现（决策 8）＋ 配置同步（`application-develop.yml` / `application-develop-mysql.yml` / `application-product.yml` / `pre-release/config.yml` / `docs/quick-start/config.md`）＋ 文档同步（本文件、路线图、档位 3、评估报告、`microservices/README.md`）。

**目标**：网关**不再向 core 询问会话**——用环境变量注入的密钥自己验签用户凭证，并把**凭证原值透传**给下游。

## 8. 学习点

| 学习点 | 在哪被逼出来 |
|---|---|
| **网关模式与同源策略** | 唯一入口是"同源"这个浏览器约束的直接结果，而不是架构偏好 |
| **策略 / 传输分离** | 决策 4：把"能不能转"与"怎么转"分开，才能既用官方库又不把判定逻辑搬出信任边界 |
| **边界是画出来的，不是自然长出来的** | 8.8 把判定从 core 收回网关后，"策略 / 传输分离"的说法已经过期——**判定与传输都在网关，core 只剩业务与凭证签发**。原先的"分离"其实是"core 兼职控制面"的委婉说法 |
| **信任边界必须是结构性的** | 决策 3.4：先把它做成"**唯一注入点**"，再补"**入站同类头全剥离**"——两条缺一不可 |
| **改判要留下理由，而不是只改结论** | 决策 3.2：原方案曾明确否决"网关自己验会话"，本次改判的原因是**需求变了**（不再允许"验证凭证必须问 core"），不是原论证被推翻。只写新结论的文档，会让后来者以为两个决策里必有一个是错的 |
| **技术债要显式记账** | §2 的债务表 + [`docs/plan/todo.md`](../todo.md)：写明债务、到期条件与部署兜底，而不是含糊的"以后再说" |
| **"剥离得更干净"不等于"更安全"** | 凭证三入口的处置反转（决策 3.3）：剥离让下游只能信任明文身份头；透传让下游**能自己校验**。安全的判据是"这个决定能否让下游 fail-closed"，而不是"暴露的东西越少越好" |
| **官方库的边界** | §2：官方库覆盖传输机制，不覆盖你的策略。判断"引入官方库能省掉什么"时，必须逐条对照自己的规则清单 |
| **"实测"与"以为"的差距** | 8.1 的改判来自实测：官方 `RequestSize` 对 chunked **完全不拦**（65MB 原样到达下游）；网关会**把 `//` 折叠**。两者都无法从文档读出来 |
| **"做得到"与"该不该做"是两个问题** | 请求体上限的第三个来回：先按实测补出自定义增量拦截（能用、已取证），再按职责判断**整个移除**。技术可行是必要条件，不是充分条件——否则唯一入口会不断长出与业务无关的策略 |
| **注释处理器不再默认开启** | JDK 23+ 起 `javac` 不自动跑注解处理：不写 `<proc>full</proc>`，Lombok 会静默失效，报错形式是"找不到符号 getXxx()" |
| **成对取舍的记录方式** | 与[评估报告 §2](review/microservice-plan-review.md) 的"当时不需要、现在为什么需要"形成完整决策链 |
